# API specification

Default base URL: `http://localhost:8080`.

- Interactive Swagger UI: `/swagger-ui/index.html`
- Generated OpenAPI JSON: `/v3/api-docs`
- Generated OpenAPI YAML: `/v3/api-docs.yaml`

The generated specification describes current request/response schemas. Start
the project with [RUNNING.md](../RUNNING.md), or use the endpoint examples below
in Postman.

## Common headers

| Header                           | Requirement                                                                                                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-User-Id`                      | Required for all business endpoints; positive numeric ID with an existing local wallet. Supplied by the simulated gateway.                                    |
| `X-Request-Id`                   | Optional correlation ID, 1-64 characters matching `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`. Missing/invalid IDs are replaced by UUIDs. Returned in response headers. |
| `Content-Type: application/json` | Required for transfer requests.                                                                                                                               |
| `Idempotency-Key`                | Required for transfers; same format as the correlation ID. Unique per sender/intended payment; reused only for retries.                                       |

Business success responses use `application/json` and `Cache-Control: no-store`.
Swagger endpoints do not require a user header.

## Endpoints

| Method | Path                                  | Success                 | Purpose                                        |
| ------ | ------------------------------------- | ----------------------- | ---------------------------------------------- |
| GET    | `/api/v1/wallet`                      | 200                     | Current user's balance and external name       |
| GET    | `/api/v1/friends`                     | 200                     | Eligible external recipients, excluding caller |
| POST   | `/api/v1/transfers`                   | 201, or 200 for a retry | Validate and transfer funds                    |
| GET    | `/api/v1/transactions?page=1&size=20` | 200                     | Current user's sent/received history           |
| GET    | `/api/v1/transactions/{id}`           | 200                     | Details of a transfer involving the caller     |

### Wallet

```http
GET /api/v1/wallet
X-User-Id: 1
```

Example (balance depends on seed data and subsequent transfers):

```json
{ "userId": 1, "name": "Leanne Graham", "balance": 10000.0 }
```

### Friends

```http
GET /api/v1/friends
X-User-Id: 1
```

Example, abbreviated:

```json
[
  { "userId": 2, "name": "Ervin Howell" },
  { "userId": 3, "name": "Clementine Bauch" }
]
```

Only users returned by the external directory with local wallets are included.
No eligible friends returns `[]`. Wallet balances and full profiles are excluded.

### Send money

```http
POST /api/v1/transfers
X-User-Id: 1
Idempotency-Key: payment-001
Content-Type: application/json

{"recipientId":2,"amount":150.00}
```

`recipientId` must be positive, different from the caller, and identify both a
local wallet and a valid external profile. `amount` must be at least 0.01 with
at most 17 integer digits and two fractional digits. The sender must have enough
funds and daily allowance; the recipient's resulting balance must fit the database
amount range. The sender is derived from the header, never from the body.

Example HTTP 201 response:

```json
{
  "transferId": "11111111-1111-1111-1111-111111111111",
  "senderId": 1,
  "recipientId": 2,
  "recipientName": "Ervin Howell",
  "amount": 150.0,
  "senderBalance": 9850.0,
  "createdAt": "2026-11-05T01:00:00Z"
}
```

Retry the same key and recipient/amount to return HTTP 200 and the original
financial receipt without another payment. A changed recipient or amount with
the same key returns 409. Use a new key for a new intended payment. Current
external name lookup is still required on retries.

The daily limit is read per sender from `daily_transfer_limits`; completed
outgoing transfers within the Manila calendar day count toward it. Incoming
payments and successful replays do not consume additional allowance. Zero blocks
new payments. Missing configuration returns 503.

### Transaction history

```http
GET /api/v1/transactions?page=1&size=20
X-User-Id: 1
```

`page` defaults to 1 and must be at least 1. `size` defaults to 20 and must be
1-100. Offsets exceeding the supported integer range are rejected. Results sort
by `createdAt` descending, then transfer ID descending. Concurrent new payments
can shift offset-based pages between requests.

```json
{
  "items": [
    {
      "transferId": "11111111-1111-1111-1111-111111111111",
      "direction": "SENT",
      "counterparty": { "userId": 2, "name": "Ervin Howell" },
      "amount": 150.0,
      "createdAt": "2026-11-05T01:00:00Z"
    }
  ],
  "page": 1,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

Direction is `SENT` or `RECEIVED` relative to the caller. `counterparty` is the
recipient for sent transfers and the sender for received transfers. Empty
history or pages beyond the end return empty `items` with pagination metadata.

### Transaction details

Use a UUID returned by send money or history:

```http
GET /api/v1/transactions/11111111-1111-1111-1111-111111111111
X-User-Id: 1
```

```json
{
  "transferId": "11111111-1111-1111-1111-111111111111",
  "direction": "SENT",
  "sender": { "userId": 1, "name": "Leanne Graham" },
  "recipient": { "userId": 2, "name": "Ervin Howell" },
  "amount": 150.0,
  "createdAt": "2026-11-05T01:00:00Z"
}
```

Only the sender/recipient may view details. Missing and unrelated IDs return the
same 404 response. History and details never expose balance snapshots or retry
keys. External names are current, not historical snapshots; unavailable profiles
or directory outages produce null names while financial data remains accessible.

## Errors

Handled errors contain only `detail`; HTTP status and `X-Request-Id` remain in the
response status/headers. Specific internal reasons are available in correlated
server logs. No `status`, `title`, or `instance` fields are added to handled
error bodies.

| Status | Cases                                                                                                   | Detail                                                                            |
| ------ | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 400    | Missing/invalid identity, invalid body/pagination/UUID/key, self-transfer, externally missing recipient | `Invalid request.`                                                                |
| 404    | Missing local wallet, missing or unrelated transaction                                                  | `Requested resource not found.`                                                   |
| 409    | Insufficient funds                                                                                      | `Insufficient balance. Your wallet balance is too low to complete this transfer.` |
| 409    | Daily limit exceeded                                                                                    | `Daily transfer limit exceeded. Reduce the amount or try again tomorrow.`         |
| 409    | Conflicting retry key or recipient balance overflow                                                     | `Unable to process your request.`                                                 |
| 500    | Database access/storage failure                                                                         | `Unable to process your request.`                                                 |
| 502    | External failure for wallet, friends, or transfer validation                                            | `Unable to process your request.`                                                 |
| 503    | Missing sender daily-limit configuration                                                                | `Unable to process your request.`                                                 |

```json
{ "detail": "Invalid request." }
```

These are the application's handled error contracts. Framework-level errors
such as unsupported routes/methods or media types may use Spring's default response.
