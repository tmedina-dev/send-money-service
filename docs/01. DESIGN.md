# Design choices

## Structure and scope

The backend is one Java 21 / Spring Boot application, organized by feature:
`wallet`, `friend`, `transfer`, and `transaction`. Controllers handle HTTP,
services implement business rules, and Spring Data JPA repositories access
PostgreSQL. Shared identity validation, errors, logging, and OpenAPI configuration
live in `common`. A single deployment keeps financial updates in one database
transaction without introducing distributed coordination.

There is no frontend or real authentication. The upstream gateway is assumed to
authenticate callers and provide `X-User-Id`; the backend validates that ID against
local wallets. This header simulation is not a replacement for gateway security.
History and details queries restrict records to the caller as sender or recipient.
Missing and unrelated transfer IDs both produce 404.

## Data and money

- PostgreSQL is Dockerized, with named volumes for database data and file logs.
  Flyway applies versioned schema and demo-data migrations on startup.
- One wallet exists per external user ID. Names and other profiles remain in
  JSONPlaceholder and are not stored locally.
- All monetary values represent PHP. Java uses `BigDecimal`; database amounts
  use `NUMERIC(19,2)`. API validation rejects nonpositive amounts and excess scale.
- `wallets.balance` supports fast reads and payment checks. `money_transfers`
  stores completed transfers. Both change together; failed transfers leave no
  history row. Seeded opening balances are demo funding, not ledger entries, so
  this is not a complete double-entry accounting ledger.

## Transfer correctness

`TransferService` validates the caller, request, recipient wallet, and external
recipient profile. It calls a separate `TransferExecutionService` bean so Spring's
`@Transactional` proxy controls the entire financial operation. External HTTP
requests finish before database locks are acquired.

Execution locks both wallets in ascending user-ID order, reducing deadlock risk
for opposing payments. While holding the locks, it checks the retry key, available
balance, recipient balance capacity, and the sender's daily limit. The two balance
updates and history insert commit together or roll back together.

The database enforces unique `(sender_user_id, idempotency_key)` pairs. The same
key and amount/recipient returns the original financial receipt without another
debit; a changed payload returns 409. A balance snapshot preserves the original
receipt even after later payments. Retries still perform external recipient
validation, and the recipient name reflects the current external profile.

Daily limits come from `daily_transfer_limits`. The service sums outgoing
transfers within the current `Asia/Manila` calendar day: inclusive midnight to
exclusive next midnight. Incoming transfers do not count. Exact-limit payments
are allowed; zero blocks outgoing payments; missing configuration fails closed
with 503. An injected `Clock` gives the limit check and stored transfer the same
timestamp and allows deterministic midnight tests. No reset job is required.

## External integration and responses

`UserDirectoryClient` uses HTTP with a three-second connection timeout and a
five-second read timeout. Response DTOs combine local financial data with the
necessary external names rather than exposing full profiles or JPA entities.
Friends are external users with local wallets, excluding the caller; there is no
separate friendship relationship table.

History uses one-based pagination, a maximum page size of 100, and descending
timestamp/ID ordering. One directory list lookup enriches each nonempty response,
avoiding a separate request per transaction. Names become null if unavailable,
preserving access to financial history. Wallet and friends lookups instead return
502 on external failure; transfers cannot proceed without recipient validation.
History/details omit wallet balances and private retry keys.

## Operations and verification

`X-Request-Id` is accepted when valid or generated otherwise, returned to the
caller, included in logging context, and forwarded downstream. Console and dated
file logs include method, path, status, and duration. Logging context is cleared
after requests. Public errors contain only `detail`; business failures such as
insufficient balance and daily limits have specific messages.

Docker Compose builds the application from source and waits for database and
backend health checks. A non-root Java runtime writes to the log volume. See
[RUNNING.md](../RUNNING.md) for startup, ports, persistence, and troubleshooting.
Image builds skip tests; Maven integration tests separately use isolated
PostgreSQL Testcontainers and stub external services. Tests cover ownership,
validation, rollback, concurrent payments, retry protection, daily boundaries,
pagination, and directory outages.
